# Requirements Document

## Introduction

This document specifies requirements for a GPU-accelerated fuzzy rule mining trading pipeline (`gpu-fuzzy-trading-pipeline`). The system is a complete, ground-up rewrite of the previous `bigdata_trader` package, incorporating lessons learned from that implementation. The pipeline mines fuzzy trading rules from a discretized feature dataset, optimizes them using GPU-accelerated evolutionary algorithms, refines risk parameters via deep reinforcement learning, and produces two JSON files (`long.json` and `short.json`) that are fully compatible with `evaluator_v3.ipynb`.

The pipeline operates in five sequential phases:
1. **Feature Selection** — direction-specific, mode-aware feature ranking
2. **Rule Pool Generation** — GPU-accelerated multi-objective evolutionary search
3. **Rule Set Selection** — combinatorial optimization to assemble final rule teams
4. **RL-Based Risk Optimization** — dynamic TP/SL/capital tuning via a DRL agent
5. **Out-of-Sample Test** — final evaluation on held-out `test.csv`

All hyperparameters are controlled through a single `config.py` file. No runtime flags are used.

## Glossary

- **Pipeline**: The end-to-end system described in this document.
- **Feature**: A pre-engineered, discretized indicator column in the dataset (not a label or meta column).
- **Feature Mode**: The discretization type of a feature column: `binary`, `ternary`, `positive`, `sparse_positive`, `sparse_signed`, or `signed`.
- **Fuzzy Value Name**: A human-readable label for a discretized feature value (e.g., "Very High", "Extreme Bullish", "Active (1)").
- **Rule**: A set of conditions of the form `[feature_name] IS Fuzzy Value Name`, combined with AND logic, plus associated `tp`, `sl`, and `capital_pct` parameters.
- **Rule Set**: An ordered list of 2–5 Rules evaluated with priority-based assignment (first matching rule wins per candle).
- **Long Strategy / Short Strategy**: A Rule Set with `direction` set to `"long"` or `"short"` respectively.
- **Rule Pool**: A large collection of candidate Rules generated by Phase 2 before selection.
- **Backtest Engine**: The trade simulation logic that exactly mirrors `evaluator_v3.ipynb`'s `CapitalManagedTradeSimulator`.
- **Symbol**: One of the 10 trading instruments present in the dataset.
- **Chronological Split**: A per-symbol time-ordered split of `train.csv` into 75% train and 25% validation subsets.
- **Label Columns**: Look-ahead columns used only for trade outcome simulation: `label_open_next`, `label_close_288`, `label_min_288`, `label_max_288`, `label_max_before_min`.
- **Meta Columns**: Non-feature, non-label columns: `datetime`, `symbol`.
- **MAX_HOLD_CANDLES**: The maximum number of candles a trade is held open (288), matching the evaluator constant.
- **TP**: Take-profit percentage.
- **SL**: Stop-loss percentage.
- **capital_pct**: Percentage of current equity allocated as notional for a single trade.
- **MOEA/D**: Multi-Objective Evolutionary Algorithm based on Decomposition.
- **MOPSO**: Multi-Objective Particle Swarm Optimization.
- **NSGA-II**: Non-dominated Sorting Genetic Algorithm II.
- **RVEA**: Reference Vector guided Evolutionary Algorithm.
- **EvoX**: A JAX-based evolutionary computation library.
- **DRL Agent**: Deep Reinforcement Learning agent (DDPG or PPO).
- **Elbow Method**: A technique to identify the optimal stopping point in a learning curve by finding the point of maximum curvature.
- **FEE_PCT**: Round-trip trading fee percentage (0.20%), matching the evaluator constant.
- **INITIAL_CAPITAL**: Starting account equity (1000.0), matching the evaluator constant.
- **LEVERAGE**: Position leverage multiplier (1.0), matching the evaluator constant.
- **MAX_TOTAL_EXPOSURE_PCT**: Maximum total notional exposure as a percentage of equity (100.0%), matching the evaluator constant.
- **Pareto Front**: The set of non-dominated solutions in a multi-objective optimization.
- **PSO**: Particle Swarm Optimization.
- **GWO**: Grey Wolf Optimizer.
- **FRST**: Fuzzy Rough Set Theory.

## Requirements

### Requirement 1: Single Configuration Source of Truth

**User Story:** As a researcher, I want all hyperparameters and paths in one file, so that I can tune the pipeline without hunting through multiple modules.

#### Acceptance Criteria

1. THE Pipeline SHALL read all hyperparameters, file paths, and behavioral toggles exclusively from `config.py`.
2. WHEN a runtime flag or command-line argument that would override a `config.py` value is provided, THE Pipeline SHALL ignore it and continue using the `config.py` value.
3. THE `config.py` SHALL define at minimum: dataset paths, label column names, meta column names, TP/SL bounds, capital sizing limits, FEE_PCT, INITIAL_CAPITAL, LEVERAGE, MAX_HOLD_CANDLES, MAX_TOTAL_EXPOSURE_PCT, Phase 1 evolutionary algorithm settings, Phase 2 selection settings, Phase 3 RL agent settings, and output directory paths.

---

### Requirement 2: Data Loading and Preparation

**User Story:** As a researcher, I want the pipeline to load and split the dataset correctly, so that there is no temporal leakage between training and validation.

#### Acceptance Criteria

1. THE Data_Loader SHALL load `data/train.csv` and `data/test.csv` using comma-separated format with automatic datetime parsing.
2. WHEN loading data, THE Data_Loader SHALL sort rows by `datetime` within each symbol.
3. THE Data_Loader SHALL drop the last 288 rows per symbol (where labels are absent) from both `train.csv` and `test.csv` before any processing.
4. THE Data_Loader SHALL drop all rows where any label column (`label_open_next`, `label_close_288`, `label_min_288`, `label_max_288`, `label_max_before_min`) is NaN.
5. THE Data_Loader SHALL fill NaN values in feature columns with 0 after label-row removal.
6. THE Data_Splitter SHALL split `train.csv` into train (75%) and validation (25%) subsets **per symbol** using chronological order, preserving each symbol's temporal sequence independently.
7. THE Data_Splitter SHALL NOT perform a global split across all symbols simultaneously.
8. THE Data_Splitter SHALL persist the split datasets to `data/train_75.parquet` and `data/validation_25.parquet` for reuse across pipeline runs.

---

### Requirement 3: Feature Mode Detection

**User Story:** As a researcher, I want features automatically classified by their discretization type, so that encoding and rule generation respect each feature's value space.

#### Acceptance Criteria

1. THE Feature_Detector SHALL classify each feature column into exactly one of six modes: `binary`, `ternary`, `positive`, `sparse_positive`, `sparse_signed`, or `signed`.
2. THE Feature_Detector SHALL use the following detection logic:
   - IF unique non-NaN values are a subset of {0, 1} AND count ≤ 2, THEN mode is `binary`.
   - IF unique non-NaN values are a subset of {-1, 0, 1} AND count ≤ 3, THEN mode is `ternary`.
   - IF minimum value < 0 AND zero ratio > 0.3, THEN mode is `sparse_signed`.
   - IF minimum value < 0 AND zero ratio ≤ 0.3, THEN mode is `signed`.
   - IF minimum value ≥ 0 AND zero ratio > 0.3, THEN mode is `sparse_positive`.
   - IF minimum value ≥ 0 AND zero ratio ≤ 0.3, THEN mode is `positive`.
3. THE Feature_Detector SHALL detect modes from the training split only, not from validation or test data.

---

### Requirement 4: Fuzzy Value Name Encoding

**User Story:** As a researcher, I want feature values encoded as human-readable fuzzy labels, so that generated rules are compatible with `evaluator_v3.ipynb`.

#### Acceptance Criteria

1. THE Encoder SHALL map discretized integer gene values to Fuzzy Value Names using the following exact mappings:
   - `binary`: 0 → "Inactive (0)", 1 → "Active (1)"
   - `ternary`: 0 → "Negative (-1)", 1 → "Neutral (0)", 2 → "Positive (1)"
   - `positive` / `sparse_positive`: 0 → "Very Low", 1 → "Low", 2 → "Medium", 3 → "High", 4 → "Very High"
   - `sparse_signed`: 0 → "Strong Negative", 1 → "Weak Negative", 2 → "Exactly Zero", 3 → "Weak Positive", 4 → "Strong Positive"
   - `signed`: 0 → "Extreme Bearish", 1 → "Strong Bearish", 2 → "Bearish", 3 → "Weak Bearish", 4 → "Neutral Negative", 5 → "Neutral Positive", 6 → "Weak Bullish", 7 → "Bullish", 8 → "Strong Bullish", 9 → "Extreme Bullish"
2. THE Encoder SHALL format each condition as `[feature_name] IS Fuzzy Value Name` with square brackets around the feature name.
3. THE Encoder SHALL use a "don't care" sentinel value equal to `num_classes` for each mode (2 for binary, 3 for ternary, 5 for positive/sparse_positive/sparse_signed, 10 for signed) to represent inactive conditions in a chromosome.
4. IF a chromosome contains a sentinel value that does not equal `num_classes` for its corresponding mode, THEN THE Encoder SHALL reject the chromosome and raise a configuration error requiring manual correction.

### Requirement 5: Backtest Engine — Evaluator Compatibility

**User Story:** As a researcher, I want the internal backtest engine to exactly replicate `evaluator_v3.ipynb` semantics, so that scores during optimization match final evaluation scores.

#### Acceptance Criteria

1. THE Backtest_Engine SHALL implement priority-based rule assignment: for each candle, the first rule in the ordered Rule Set whose conditions all match is assigned; subsequent rules are skipped for that candle.
2. THE Backtest_Engine SHALL compute trade outcomes using the following logic:
   - For `long` direction: TP is hit when `label_max_288 >= entry_price * (1 + tp/100)`; SL is hit when `label_min_288 <= entry_price * (1 - sl/100)`; when both are hit, `label_max_before_min == 1` means TP first, otherwise SL first; time exit uses `label_close_288`.
   - For `short` direction: TP is hit when `label_min_288 <= entry_price * (1 - tp/100)`; SL is hit when `label_max_288 >= entry_price * (1 + sl/100)`; when both are hit, `label_max_before_min == 1` means SL first, otherwise TP first; time exit uses `label_close_288`.
3. THE Backtest_Engine SHALL use `label_open_next` as the entry price for all trades.
4. THE Backtest_Engine SHALL apply capital-managed position sizing: `position_notional = equity * (capital_pct / 100) * leverage`, capped by remaining total exposure capacity.
5. THE Backtest_Engine SHALL reserve exposure for each open trade until `entry_symbol_bar_index + MAX_HOLD_CANDLES`, using conservative release semantics identical to `evaluator_v3.ipynb`.
6. THE Backtest_Engine SHALL deduct `FEE_PCT / 100` of position notional as round-trip fee from each trade's gross PnL.
7. THE Backtest_Engine SHALL track equity, peak equity, drawdown, win/loss counts, and profit factor across all realized trades.
8. THE Backtest_Engine SHALL stop simulation and mark the account as ruined when equity drops to or below 0.
9. THE Backtest_Engine SHALL skip trades where computed position notional is below `MIN_POSITION_NOTIONAL` (1.0).
10. THE Backtest_Engine SHALL use `INITIAL_CAPITAL = 1000.0`, `LEVERAGE = 1.0`, `FEE_PCT = 0.20`, `MAX_HOLD_CANDLES = 288`, `MAX_TOTAL_EXPOSURE_PCT = 100.0` as defaults, all overridable via `config.py`.

---

### Requirement 6: GPU-Accelerated Backtest Engine

**User Story:** As a researcher, I want a GPU-accelerated version of the backtest engine, so that evolutionary search over thousands of candidate rules completes in reasonable time.

#### Acceptance Criteria

1. THE GPU_Backtest_Engine SHALL produce results numerically equivalent to the CPU Backtest_Engine for the same rule set and dataset (within floating-point tolerance).
2. THE GPU_Backtest_Engine SHALL implement the same priority-based assignment, capital management, exposure reservation, and fee deduction logic as the CPU engine.
3. THE GPU_Backtest_Engine SHALL use JAX (preferred) or PyTorch for GPU tensor operations.
4. WHEN a GPU is not available, THE GPU_Backtest_Engine SHALL fall back to CPU execution transparently.
5. IF CPU fallback cannot be initialized, THEN THE GPU_Backtest_Engine SHALL fail immediately with a descriptive error.
6. THE GPU_Backtest_Engine SHALL be benchmarked against the CPU engine before use in Phase 2, and the benchmark SHALL confirm numerical parity within 1e-4 relative tolerance on sampled rules.

---

### Requirement 7: Phase 1 — Direction-Specific Feature Selection

**User Story:** As a researcher, I want the pipeline to select the most predictive features separately for long and short directions, so that rule generation starts from a relevant, non-redundant feature subset.

#### Acceptance Criteria

1. THE Feature_Selector SHALL produce two independent feature lists: one for the long direction and one for the short direction.
2. THE Feature_Selector SHALL exclude all label columns and meta columns from consideration.
3. THE Feature_Selector SHALL build a direction-specific trade-success target from the label columns (e.g., for long: whether `label_max_288` exceeds entry by TP threshold before `label_min_288` drops by SL threshold).
4. THE Feature_Selector SHALL score features using at least one of: mutual information, tree-based importance, PSO wrapper, GWO wrapper, or Fuzzy Rough Set Theory relevance.
5. THE Feature_Selector SHALL remove features with near-zero dispersion (e.g., more than 95% identical values) before scoring.
6. THE Feature_Selector SHALL measure feature stability across symbols (score consistency across the 10 symbols) and penalize unstable features.
7. THE Feature_Selector SHALL group features by mode and apply redundancy removal within each mode group.
8. THE Feature_Selector SHALL persist results to `outputs/selected_features_long.json` and `outputs/selected_features_short.json`, each containing feature names, modes, and selection scores.
9. WHEN feature selection outputs already exist, THE Pipeline SHALL validate that the files are readable and structurally valid before skipping Phase 1; IF the files are missing, unreadable, or corrupted, THEN THE Pipeline SHALL fail immediately and require manual intervention.

---

### Requirement 8: Phase 2 — GPU-Accelerated Rule Pool Generation

**User Story:** As a researcher, I want a large, diverse pool of candidate fuzzy rules generated via GPU-accelerated multi-objective evolutionary search, so that Phase 3 has high-quality material to select from.

#### Acceptance Criteria

1. THE Rule_Pool_Generator SHALL generate separate rule pools for the long direction and the short direction.
2. THE Rule_Pool_Generator SHALL use a multi-objective evolutionary algorithm (MOPSO, MOEA/D, or RVEA) implemented via EvoX/EvoMO (JAX-based, preferred) or EvoTorch/PyTorch.
3. THE Rule_Pool_Generator SHALL optimize three objectives simultaneously: maximize total return, minimize maximum drawdown, and maximize win rate.
4. DURING Phase 2, THE Rule_Pool_Generator SHALL use static risk parameters: TP=4%, SL=2%, capital_pct=50%.
5. EACH candidate rule chromosome SHALL encode: a feature selection mask (which features are active) and a value assignment for each active feature (one of the valid discretized values for that feature's mode).
6. THE Rule_Pool_Generator SHALL enforce a minimum number of active conditions per rule (configurable in `config.py`, default: 2) and a maximum (configurable, default: 5).
7. THE Rule_Pool_Generator SHALL evaluate candidate rules using the GPU_Backtest_Engine on the training split.
8. THE Rule_Pool_Generator SHALL apply a diversity penalty to discourage the pool from collapsing to a single pattern.
9. THE Rule_Pool_Generator SHALL apply a trade-support penalty to rules that trigger fewer than a configurable minimum number of trades (default: 20) across all symbols.
10. THE Rule_Pool_Generator SHALL persist the final Pareto-front rule pool to `outputs/phase2_long_pool.json` and `outputs/phase2_short_pool.json`.
11. THE Rule_Pool_Generator SHALL persist generation history metrics to `outputs/phase2_long_history.json` and `outputs/phase2_short_history.json`.
12. WHEN rule pool outputs already exist, THE Pipeline SHALL skip Phase 2 and load the existing files.

---

### Requirement 9: Phase 3 — Rule Set Selection

**User Story:** As a researcher, I want the best combination of 2–5 rules selected from the Phase 2 pool, so that the final strategy is compact, diverse, and robust across symbols.

#### Acceptance Criteria

1. THE Rule_Set_Selector SHALL select an ordered Rule Set of 2–5 rules from the Phase 2 pool for each direction independently.
2. THE Rule_Set_Selector SHALL use NSGA-II or a similar combinatorial multi-objective optimizer to search over rule combinations.
3. THE Rule_Set_Selector SHALL evaluate candidate Rule Sets using the CPU Backtest_Engine on the validation split (not the training split).
4. THE Rule_Set_Selector SHALL enforce that no two rules in a selected Rule Set are identical (same conditions).
5. THE Rule_Set_Selector SHALL apply a coverage penalty to Rule Sets where fewer than a configurable minimum number of symbols generate at least one trade; WHEN the minimum is set to zero, THE Rule_Set_Selector SHALL still apply a penalty to Rule Sets that generate zero trades across all symbols.
6. THE Rule_Set_Selector SHALL apply a train/validation agreement penalty to Rule Sets where validation performance deviates significantly from training performance (to reduce overfitting).
7. THE Rule_Set_Selector SHALL output `outputs/long.json` and `outputs/short.json` in the exact format required by `evaluator_v3.ipynb`:
   ```json
   {
     "direction": "long",
     "rules_set": [
       {
         "tp": <float>,
         "sl": <float>,
         "capital_pct": <float>,
         "conditions": ["[feature_name] IS Fuzzy Value Name", ...]
       }
     ]
   }
   ```
8. WHEN rule set selection outputs already exist and pass validation, THE Pipeline SHALL skip Phase 3 and load the existing files; IF only one of `long.json` or `short.json` exists, THE Pipeline SHALL skip Phase 3 and proceed with the available file, leaving the missing file absent.

---

### Requirement 10: Phase 4 — RL-Based Dynamic Risk Optimization

**User Story:** As a researcher, I want a DRL agent to fine-tune TP, SL, and capital_pct for each rule, so that risk parameters are optimized beyond the static Phase 2 defaults.

#### Acceptance Criteria

1. THE RL_Agent SHALL be implemented as a DDPG or PPO agent using stable-baselines3 or a custom PyTorch implementation.
2. THE RL_Agent SHALL observe a state vector comprising: current market feature values at each candle, fuzzy rule activation strengths (how many conditions of each rule are satisfied), and current portfolio state (equity, open exposure).
3. THE RL_Agent SHALL output continuous actions: TP in [1%, 10%], SL in [0.5%, 5%], capital_pct in [10%, 100%] for each rule in the Rule Set.
4. THE RL_Agent SHALL be trained on the training split and evaluated on the validation split.
5. THE RL_Agent SHALL use the Elbow Method on validation performance curves to identify the optimal training checkpoint, preventing overfitting to the training split; THE Elbow Method SHALL run during training and identify checkpoints as soon as validation curves are available, without waiting for full training to complete.
6. THE RL_Agent SHALL update `outputs/long.json` and `outputs/short.json` with the RL-optimized `tp`, `sl`, and `capital_pct` values per rule.
7. THE RL_Agent SHALL be trained separately for the long strategy and the short strategy.
8. WHEN RL optimization outputs already exist and pass validation, THE Pipeline SHALL skip Phase 4 and treat training and validation as complete.

---

### Requirement 11: Phase 5 — Out-of-Sample Test

**User Story:** As a researcher, I want the final strategies evaluated on the held-out test set, so that I can assess true out-of-sample generalization.

#### Acceptance Criteria

1. THE OOS_Evaluator SHALL load `outputs/long.json` and `outputs/short.json` as produced by Phase 4.
2. THE OOS_Evaluator SHALL load `data/test.csv` and apply the same data preparation steps as Phase 1 (drop last 288 rows per symbol, drop NaN label rows, fill feature NaNs with 0).
3. THE OOS_Evaluator SHALL evaluate both strategies using the CPU Backtest_Engine with `return_logs=True`.
4. THE OOS_Evaluator SHALL report: total return %, max drawdown %, win rate %, profit factor, executed trades, and account status (survived / ruined) for each strategy; WHEN no trades were executed, THE OOS_Evaluator SHALL report 0% total return and SHALL NOT report account ruin unless actual trading losses caused equity to reach zero.
5. THE OOS_Evaluator SHALL generate per-symbol performance breakdowns for both strategies.
6. THE OOS_Evaluator SHALL save performance reports to `outputs/reports/test_long_report.json`, `outputs/reports/test_short_report.json`, and `outputs/reports/test_per_symbol_performance.csv`.
7. THE OOS_Evaluator SHALL generate equity curve plots saved to `outputs/reports/test_long_equity.png` and `outputs/reports/test_short_equity.png`.

---

### Requirement 12: JSON Output Format Compatibility

**User Story:** As a researcher, I want the output JSON files to be exactly compatible with `evaluator_v3.ipynb`, so that the evaluator can load and run them without modification.

#### Acceptance Criteria

1. THE Output_Writer SHALL produce `long.json` and `short.json` with the top-level keys `"direction"` and `"rules_set"`.
2. THE `"direction"` field SHALL be the string `"long"` or `"short"` (lowercase).
3. THE `"rules_set"` field SHALL be a JSON array of rule objects, each containing exactly the keys `"tp"`, `"sl"`, `"capital_pct"`, and `"conditions"`.
4. THE `"tp"` and `"sl"` values SHALL be floating-point numbers representing percentages (e.g., 2.5 means 2.5%).
5. THE `"capital_pct"` value SHALL be a floating-point number representing the percentage of equity to allocate (e.g., 50.0 means 50%).
6. THE `"conditions"` field SHALL be a non-empty JSON array of strings, each in the format `"[feature_name] IS Fuzzy Value Name"`.
7. THE Fuzzy Value Names in conditions SHALL exactly match the names recognized by `evaluator_v3.ipynb`'s `apply_dynamic_rule` function (see Requirement 4).
8. THE `"rules_set"` array SHALL contain between 2 and 5 rule objects; IF the rule generation algorithm produces more than 5 rules, THE Output_Writer SHALL truncate to the first 5 rules.
9. EACH rule object in `"rules_set"` SHALL have at least one of `"tp"`, `"sl"`, or `"capital_pct"` with a non-zero value; IF all three are zero, THEN THE Output_Writer SHALL reject that rule object.

---

### Requirement 13: Pipeline Orchestration and Skip Logic

**User Story:** As a researcher, I want the pipeline to skip completed phases automatically, so that I can resume interrupted runs without recomputing from scratch.

#### Acceptance Criteria

1. THE Pipeline_Orchestrator SHALL execute phases in order: Phase 1 → Phase 2 → Phase 3 → Phase 4 → Phase 5.
2. WHEN a phase's output files already exist on disk, THE Pipeline_Orchestrator SHALL validate those files before skipping; IF the files are valid and compatible with the current pipeline configuration, THE Pipeline_Orchestrator SHALL skip that phase and load the existing outputs; IF the files are invalid or incompatible, THE Pipeline_Orchestrator SHALL re-run that phase.
3. THE Pipeline_Orchestrator SHALL log the start time, end time, and elapsed duration of each phase.
4. THE Pipeline_Orchestrator SHALL be invokable as `python -m gpu_fuzzy_trader.run_pipeline` to run all phases end-to-end.
5. THE Pipeline_Orchestrator SHALL create the `outputs/` and `outputs/reports/` directories if they do not exist.

### Requirement 14: Reporting and Visualization

**User Story:** As a researcher, I want visual dashboards and CSV summaries for each phase, so that I can diagnose pipeline behavior and compare runs.

#### Acceptance Criteria

1. THE Reporter SHALL generate a Phase 2 generation metrics plot (objectives vs. generation) saved to `outputs/reports/phase2_long_metrics.png` and `outputs/reports/phase2_short_metrics.png`.
2. THE Reporter SHALL generate train and validation equity curve plots for the selected Rule Sets, saved to `outputs/reports/train_long_equity.png`, `outputs/reports/train_short_equity.png`, `outputs/reports/validation_long_equity.png`, and `outputs/reports/validation_short_equity.png`.
3. THE Reporter SHALL generate per-symbol performance CSV files for train and validation splits: `outputs/reports/train_per_symbol_performance.csv` and `outputs/reports/validation_per_symbol_performance.csv`.
4. THE Reporter SHALL generate a Phase 4 RL training curve plot (validation return vs. training step) saved to `outputs/reports/phase4_long_rl_curve.png` and `outputs/reports/phase4_short_rl_curve.png`, with the Elbow Method stopping point marked.

---

### Requirement 15: Symbol-Aware Evaluation

**User Story:** As a researcher, I want all backtest evaluations to be symbol-aware, so that performance is measured consistently across all 10 trading instruments.

#### Acceptance Criteria

1. THE Backtest_Engine SHALL track per-symbol trade counts, win rates, and net PnL for every evaluation.
2. THE Feature_Selector SHALL score features per symbol and report cross-symbol stability metrics.
3. THE Rule_Pool_Generator SHALL evaluate candidate rules across all symbols in the training split, not on a single aggregated dataset.
4. THE Rule_Set_Selector SHALL penalize Rule Sets that generate zero trades on more than a configurable number of symbols (default: 3 out of 10).
5. THE OOS_Evaluator SHALL report per-symbol metrics for both long and short strategies on the test set.
